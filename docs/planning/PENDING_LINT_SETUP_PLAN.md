*Gives this package a working linter. It has an `npm run lint` script and the
ESLint dependencies installed, but no configuration — so the script has never
been runnable, in this repository or the monorepo it came from.*

**Status notes**: created August 2026 during the phase-4 lift. §3 asks
one question before it is executable.
**Why this priority**: pure hygiene, no behaviour change. Worth doing because a
lint script that cannot run is worse than none: it reads as coverage that does
not exist.
**Origin**: found by phase 4's `make verify`, which ran the script for the
first time. ESLint has required a flat config since version 9; none exists
here, and none existed in the monorepo either. Its CI ran
`npm run build && npm test` only, so the gap was never exercised.
**Components**: `eslint.config.js` (new), `Makefile` (`verify`, and the
comment above it), and whatever the first clean run requires of `src/`.
`.github/workflows/ci.yml` needs no change: its "Verify" step runs
`make verify`, so lint reaches CI when it reaches `verify`.

## 1. What is actually missing

`package.json` has the script and the dependencies —
`eslint`, `@typescript-eslint/parser`, `@typescript-eslint/eslint-plugin` — but
no `eslint.config.js`, no `.eslintrc.*`, and no `eslintConfig` block. The
installed ESLint is 10.8.0 (`eslint ^10.8.0`), with `@typescript-eslint` 8.65.0,
whose peer range admits ESLint 10. ESLint 9 removed the implicit-default
behaviour that older versions had and 10 keeps it removed, so the script exits
with a configuration error rather than linting anything.

Nothing here is broken by the lift. The script was already inert; running it in
`verify` is simply the first time anyone asked it to work.

## 2. Sequence

1. Add a flat `eslint.config.js` with the TypeScript parser and plugin, scoped to
   `src/`.
2. Run it and see the damage. Expect the count to be large — this is code that
   has never been linted.
3. Fix or explicitly disable, in that order. A rule disabled with a reason is
   fine; a rule disabled to make the number go down is how a lint config becomes
   decoration.
4. Exclude `src/generated/` — it is generated from the chain's protobufs and
   regenerated by `make proto-sync`, so lint findings there are unfixable here
   and would have to be re-fixed on every regeneration.
5. Add `npm run lint` to `make verify`, and remove the note it currently
   prints together with the comment above the target explaining why lint is
   absent.

## 3. Open question

1. **Which rule set?** The Go side of the project runs golangci-lint at
   "v1-parity" — deliberately restoring an older, narrower surface rather than
   adopting every new check, on the grounds that a working codebase should not
   be churned for style opinions. *Recommendation*: mirror that instinct —
   `@typescript-eslint/recommended` without the type-checked variants, which
   catches real defects (floating promises, unsafe `any` flows are in the
   type-checked set, so this is mostly correctness-lite) without imposing a
   house style on existing code. Revisit the type-checked rules once the base
   set is clean, as a separate decision.

## 4. What this plan does not solve

- **Formatting.** No Prettier, and this plan does not add one. Formatting and
  linting are separate arguments, and conflating them is how both stall.
- **The example scripts.** They are not in this repository: the chain's e2e
  driver holds them (`timeflareio/chain` — `devnet/e2e/`), so linting them is
  the chain's decision.
